# Unity NullReferenceException 조기 감지 기법 조사

Unity에서 나는 NRE는 대개 네 곳에서 생깁니다. 인스펙터 연결 누락, 초기화 순서, 파괴된 객체, 플레이 사이에 남은 static 상태입니다. 컴파일러 하나로는 이 넷을 다 잡지 못합니다. 그래서 공식 · 커뮤니티 자료도 단계별로 나눠 막는 방식을 권합니다. 아래는 문제가 일찍 드러나는 단계부터 정리한 것입니다.

## 1. 코드를 쓰는 중: Unity 전용 정적 분석기

- **Microsoft.Unity.Analyzers**: Unity 객체에 아래 문법을 쓰면 Correctness(정확성) 오류로 표시합니다.
  - `??` (UNT0007), `?.` (UNT0008), `??=` (UNT0023), `is null` (UNT0029)
  - `GetComponent` 를 자기 객체에 부르면 `RequireComponent` 를 쓰라고 권하는 규칙(UNT0039)도 있습니다.
  - VS Code용 공식 Unity 확장에 함께 들어 있어서, 지금 쓰시는 VS Code에는 확장만 설치하면 됩니다. Rider는 같은 검사를 자체 기능으로 제공합니다.
- **이 문법들이 위험한 이유**: Unity는 `UnityEngine.Object` 의 `==` 를 재정의해서 "파괴됨"도 null로 판정합니다(이른바 fake null). 그런데 `?.` · `??` 는 이 재정의를 거치지 않습니다. 그래서 파괴된 객체가 null 검사를 통과하고, 나중에 예외가 납니다.
- **한계**: 위 분석기는 IDE 안에서만 돕니다. Unity 컴파일 단계(커밋 전 게이트)에서도 돌리려면 분석기 DLL을 `Assets` 에 넣고 `RoslynAnalyzer` 라벨을 붙여야 합니다. 적용 범위는 asmdef로 제한할 수 있습니다(Unity 매뉴얼).

## 2. Nullable 참조 형식(NRT): 효과는 일부만

- **설정 방법**: Unity 6.6 매뉴얼에는 컴파일러가 Roslyn이고 언어 버전이 C# 9.0이라는 것까지만 나옵니다. NRT를 켜는 방법은 공식 문서에 없습니다. 커뮤니티에서는 두 방법을 씁니다.
  - asmdef 옆에 `csc.rsp` 를 두고 `-nullable:enable` 을 적는다.
  - 파일마다 `#nullable enable` 을 적는다.
- **한계 1**: Unity API에는 nullable 표시가 없습니다. 그래서 `GetComponent` · `Find` 의 결과를 바로 써도 경고가 나지 않습니다.
- **한계 2**: `[SerializeField] Image _image = null!;` 패턴은 인스펙터로 연결하는 필드의 경고를 꺼 버립니다. 이 필드들이 Unity NRE의 가장 큰 원인이라, 정작 그 부분은 못 잡습니다.
- **정리**: 순수 C# 로직(웨이브 계산, 데이터 구조) asmdef에서는 효과가 좋습니다. MonoBehaviour의 인스펙터 연결은 3번이 맡아야 합니다.

## 3. 에디터에서 연결할 때: 직렬화 참조 검증 (효과가 가장 큼)

이 기능을 하는 Unity 공식 내장 도구는 찾지 못했습니다. 커뮤니티에서 쓰는 방법은 다음과 같습니다.

- **"필수" 표시 속성**: 비어 있으면 인스펙터에 오류를 띄웁니다.
  - NaughtyAttributes `[Required]` (MIT 라이선스, OpenUPM으로 설치)
  - unity-notnullattribute (유지보수 중단)
  - Better Validation
  - Odin Validator는 유료라 G-02에 따라 쓸 수 없습니다.
- **프로젝트 전체 스캔**: EditMode 테스트로 모든 프리팹 · 씬을 돌면서 `SerializedObject` 의 ObjectReference 속성을 검사합니다. 판정은 이렇게 합니다.
  - `objectReferenceValue == null` 이고 `objectReferenceInstanceIDValue != 0` 이면 **Missing**(연결했던 대상이 지워짐)
  - `objectReferenceValue == null` 이고 ID가 0이면 **None**(처음부터 연결 안 함)
  - `GetComponents` 결과에 null이 있으면 스크립트가 빠진 컴포넌트(Missing Script)
- **`OnValidate`**: 빈 필드를 `TryGetComponent` 로 자동으로 채울 수 있습니다. 다만 열리지 않은 씬은 다시 열어 저장하기 전까지 호출되지 않습니다.
- **`[RequireComponent]`**: 컴포넌트를 붙이는 순간에만 확인합니다. 이미 배치된 인스턴스에는 소급 적용되지 않습니다.
- **빌드에서만 나는 NRE**: 씬이 Build Settings에 빠졌거나, 참조하는 에셋이 `Editor` 폴더 안에 있는 경우가 흔합니다.

## 4. 실행 직후: 바로 실패하게 만들기(fail-fast)

- **필수 의존성을 if로 감싸지 않기**: 공식 매뉴얼의 NRE 페이지는 "null 검사 또는 try/catch"를 권합니다. 그런데 필수 의존성을 `if (x != null)` 로 감싸면 연결 실수가 조용히 숨습니다. 필수 참조는 `Awake` 에서 한 번 검사하고, 비어 있으면 `Debug.LogError(msg, this)` 로 바로 크게 실패시키는 편이 낫습니다. 콘솔에서 로그를 클릭하면 해당 객체가 하이라이트됩니다.
- **`UnityEngine.Assertions.Assert.IsNotNull`**: 기본적으로 개발 빌드에만 들어가고 릴리스 빌드에서는 빠집니다(`UNITY_ASSERTIONS` 심볼, `BuildOptions.ForceEnableAssertions`).
- **선택적 컴포넌트**: `TryGetComponent` 로 "없을 수 있음"을 코드에 드러냅니다.

## 5. static 상태: Enter Play Mode 옵션

- 도메인 리로드(Domain Reload)를 끄면 static 필드와 static 이벤트 구독이 플레이 세션 사이에 남습니다. 그러면 이미 파괴된 객체를 가리키게 됩니다.
- Unity 문서의 처방은 `[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]` 로 static을 직접 초기화하는 것입니다.
- Project Auditor의 Domain Reload 화면이 이런 문제가 있는 코드를 찾아 줍니다. 검색 결과로는 Unity 6.4부터 에디터에 내장되어 있고, 그 이전 버전은 패키지로 설치합니다.

## 6. 빌드 게이트

- `IPreprocessBuildWithReport` 에서 3번의 검증을 돌리고, 문제가 있으면 `BuildFailedException` 을 던집니다.
- 일반 `Exception` 으로는 빌드가 멈추지 않는다는 포럼 답변과 이슈 트래커 기록이 있습니다.

## Defense 에 적용한다면 (제안)

`Defense.Unity` 는 아직 만들어지기 전이라 처음부터 넣기 좋은 시점입니다. 비용이 적은 순서입니다.

3. **`Awake` fail-fast 규칙**: `Defense.Unity/CLAUDE.md` 코드 컨벤션에 넣습니다.
4. **NRT**: 순수 로직 asmdef에만 켭니다.
5. **static 초기화 규칙**: 도메인 리로드를 끌 때만 필요합니다.

# unity-cli 환경에서 NRE 감지하기

네, 방법이 있습니다. 저는 인스펙터의 빨간 표시나 콘솔 창을 눈으로 볼 수 없습니다. 그래서 모든 감지를 "명령을 실행하면 결과가 텍스트로 돌아오는" 형태로 바꿔 두는 것이 핵심입니다. 이렇게 해 두면 사람이 IDE를 볼 때보다 빠짐없이 매번 돌릴 수 있습니다.

## 지금 상태 (직접 확인함)

- `unity` CLI 1.0.0-beta.13이 설치돼 있습니다.
- 연결된 에디터는 없습니다(`unity status` 결과 `STATUS_NO_INSTANCES`).
- `Defense.Unity` 는 아직 만들기 전입니다.
- P00 계획서 S2에 이미 두 가지가 들어 있습니다. 하나는 「에디터 열림 = unity-cli / 닫힘 = batchmode」 두 갈래 게이트이고, 다른 하나는 템플릿 게이트의 PlayMode 스모크(자동 선택 + 가속 한 판)입니다. 아래 내용은 그 위에 얹으면 됩니다.

## 제가 결과를 읽을 수 있는 경로 4개

| 경로 | unity-cli에서 쓰는 방식 | 잡는 것 |
|---|---|---|
| 컴파일 진단 | `unity command recompile` 뒤 `Defense.Unity/Logs/Editor.log` 를 grep | 분석기 경고(Unity 객체에 `?.` · `??` 사용 등), nullable 경고 |
| 에디터 안에서 C# 실행 | `unity command eval`, 또는 프로젝트에 직접 넣는 `[CliCommand]` 도구 | 씬 · 프리팹의 참조 검증 |
| 테스트 러너 | 에디터가 닫혀 있으면 `unity test --mode EditMode/PlayMode`(테스트 실패 시 종료 코드 8). 에디터가 열려 있으면 `TestRunnerApi` 를 부르는 명령 | 검증 테스트, 플레이 스모크 |
| 플레이 로그 | `log_editor "== RUN n =="` 로 표지를 찍고 `editor_play` → 대기 → 정지. 그다음 Editor.log에서 표지 뒤의 `NullReferenceException\|MissingReferenceException` 을 grep | 실행 중 예외와 스택 |

`unity run --command` 는 같은 프로젝트로 이미 열린 에디터가 있으면 그것을 재사용합니다(스킬 문서). 그래서 검증 기능을 `[CliCommand]` 로 만들어 두면 에디터가 열려 있든 닫혀 있든 같은 명령으로 부를 수 있습니다.

## 시점별 감지 흐름

1. **코드를 고친 직후: 컴파일 진단**
   - Microsoft.Unity.Analyzers DLL을 `Assets/ThirdParty/` 에 넣고 `RoslynAnalyzer` 라벨을 붙입니다. 그러면 IDE가 없어도 Unity 컴파일 자체가 분석기를 돌립니다.
   - `Assets/Default.ruleset` 에서 UNT0007 · 0008 · 0023 · 0029를 **Warning 으로 고정**하고, 게이트가 이 ID의 경고를 실패로 처리합니다.
   - Error로 올리지 않는 이유가 있습니다. 컴파일 오류가 남은 채로 에디터가 다시 켜지면 Safe Mode로 뜨고, Pipeline 패키지가 로드되지 않아 unity-cli 연결이 끊깁니다(스킬 문서). 저는 그 상태에서 에디터를 조작할 수 없습니다.
   - nullable은 순수 로직 asmdef에만 `csc.rsp` `-nullable:enable` 로 켭니다.

2. **씬 · 프리팹을 연결한 직후: 참조 검증 명령**
   - 필드 연결도 제가 unity-cli로 하므로, 연결 직후 직접 만든 `validate_references` 명령을 돌려 결과를 JSON으로 받습니다.
   - 잡는 것은 세 가지입니다: 직접 만든 `[Required]` 속성이 붙은 필드가 비어 있음(None), 연결했던 대상이 지워짐(Missing), 스크립트가 빠진 컴포넌트(Missing Script).
   - 사람이 인스펙터의 빨간 표시를 보는 일을 이 명령이 대신합니다.

3. **커밋 전: 결정론 게이트**
   - **EditMode 테스트**: 모든 씬 · 프리팹 · ScriptableObject에 2번과 같은 검증을 돌립니다.
   - **PlayMode 스모크**: Unity Test Framework는 테스트 중에 Error나 Exception 로그가 나오면 기본으로 테스트를 실패 처리합니다(LogAssert). 그래서 NRE가 한 번만 나도 게이트에서 막힙니다.
   - **`Awake` 즉시 실패 검사**: 숨어 있던 null을 첫 프레임 오류로 바꿔서 스모크가 확실히 잡게 합니다.

4. **빌드 직전: 빌드 전 검증**
   - `IPreprocessBuildWithReport` 에서 빌드 씬 전체에 2번 검증을 돌리고, 문제가 있으면 `BuildFailedException` 을 던집니다.
   - 결과는 `unity build` 의 종료 코드로 받습니다.

## 이 방식으로도 못 잡는 것

- **스모크 한 판이 지나가지 않은 코드 경로의 NRE.** 어디가 실행되지 않았는지는 코드 커버리지로 볼 수 있습니다(`unity test --coverage`, `com.unity.testtools.codecoverage` 패키지 필요).
- **예외 없이 틀리게 동작하는 것.** 예를 들어 오브젝트가 보이지 않는 경우는 스크린샷(`unity command screenshot`)과 플레이검사로 확인해야 합니다.

## S2에서 확인할 것 (추정)

- **`unity test` 와 열린 에디터의 충돌**: `unity test` 는 batchmode로 에디터를 새로 띄웁니다(스킬 문서로 확인). 같은 프로젝트를 이미 연 에디터가 있으면 열리지 않을 것으로 봅니다. P00 계획서에도 같은 추정이 있습니다. 그렇다면 에디터가 열린 동안에는 `TestRunnerApi` 를 쓰는 경로가 필요합니다.
- **내장 명령 여부**: `eval`, 콘솔 읽기, 테스트 실행 명령이 Pipeline에 기본으로 들어 있는지는 에디터를 연결한 뒤 `unity command --query` 로 확인해야 합니다. 스킬 문서도 "에디터 · 패키지 버전에 따라 다르다"고 적고 있습니다.
- **csharp-ls 진단**: 이미 설치된 csharp-ls가 Unity가 만든 csproj의 분석기를 읽어 편집 중에 진단을 보여 줄 수 있을지도 확인 대상입니다. 된다면 1번 검사를 recompile 전으로 당길 수 있습니다.

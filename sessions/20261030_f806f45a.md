## 공식 입장
- **Unity**: 공식 문서는 "The plugin only ships skills and doesn't use a Model Context Protocol (MCP) server"라고만 씁니다. 문서와 블로그(2026-09-09) 어디에도 LSP, 컴파일 진단, 다른 플러그인과 같이 쓰는 법은 나오지 않습니다.
  - 짚어 둘 점이 하나 있습니다. `unity-cli` 스킬 자체가 이렇게 적고 있습니다: C# 컴파일 오류가 있으면 에디터가 Safe Mode로 뜨고, 그러면 `unity-cli`가 연결하지 못하니 `Editor.log`를 읽고 소스를 고치라는 것입니다(로컬 `skills/unity-cli/SKILL.md:40`).
  - 에디터 없이 컴파일 오류를 보여 주는 LSP가 바로 이 빈틈을 메웁니다. 이건 제 해석입니다.
- **Microsoft**: `microsoft-docs`는 Azure · .NET · Windows 문서용이고 Unity 이야기는 없습니다.
  - `csharp-ls`는 Microsoft 제품이 아닙니다(razzmatazz 개인 프로젝트, 2026-10 기준 활발히 관리 중).
  - Microsoft의 Roslyn 언어 서버를 Claude Code에 붙이는 커뮤니티 프록시도 있습니다(ClaudeCodeRoslynLspProxy, lahma/claude-roslyn-lsp). 둘 다 초기 단계입니다.
- **Anthropic 문서**: 파일을 고칠 때마다 진단이 자동으로 전달되고, LSP 도구는 읽기 전용이며, 클라우드 세션에서는 언어 서버가 뜨지 않습니다.

| `unity test`(배치 모드) | 컴파일 오류 + 테스트 실패 | 컴파일 오류면 종료 코드 6. 같은 프로젝트를 에디터가 열고 있으면 돌릴 수 없음 |
| 플레이어 빌드 | 플랫폼별 문제까지 | 몇 분 걸림. 오류를 확인하려고 쓸 일은 거의 없음 |

`unity-cli` 스킬 문서에도 이 경로(`recompile`, `Editor.log`를 `grep 'error CS'`로 읽기)가 적혀 있습니다. 그래서 LSP가 없어도 오류는 잡을 수 있습니다. 다만 고칠 때마다 에디터를 거쳐야 해서 느리고, 에디터가 꼭 열려 있어야 합니다. 또 컴파일 오류가 남은 채로 에디터를 다시 열면 Safe Mode로 빠집니다. 그러면 `unity-cli`가 연결하지 못하고 로그를 직접 읽어야 합니다.

## 역할 분담
- **LSP**: 빠른 1차 확인. 고칠 때마다 즉시 확인합니다.
- **Unity 컴파일 · 테스트**: 최종 판정입니다. `csharp-ls`는 `.csproj`를 보고 판단하는데, Unity 컴파일러에는 자체 설정(전처리 정의, C# 9 중 일부 기능 미지원)이 있어 드물게 둘이 다를 수 있습니다. 이 작업 공간의 「결정론 게이트」(커밋 전 컴파일 · 테스트)가 이 역할입니다.
- **둘 다 못 잡는 것**: 실행 중 오류(`NullReferenceException`, 인스펙터 참조가 빠진 경우, 로직 버그)는 플레이 모드와 테스트로만 드러납니다.
